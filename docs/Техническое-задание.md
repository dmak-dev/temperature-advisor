# Техническое задание на сервис подбора температуры в помещении

## 1. Общие сведения

1.1. Наименование разработки: сервис подбора рекомендуемой температуры в помещении.

1.2. Основание для разработки: ____.

1.3. Заказчик: ____. Исполнитель: ____.

1.4. Сроки начала и окончания работ: ____.

## 2. Назначение разработки

2.1. Сервис по типу помещения и текущему сезону определяет рекомендуемую температуру и возвращает её клиенту в виде ответа JSON.

2.2. Нормы температуры различаются по типу помещения: для офиса действует комфортная рабочая температура, для жилой комнаты бытовая, для склада пониженные значения. Внутри каждого типа помещения значение зависит от сезона.

2.3. Сервис рассчитан на вызов по HTTP из другого приложения, страницы и скрипта. Аутентификация и разграничение доступа не предусмотрены.

## 3. Требования к серверной части

3.1. Приложение реализуется на Python 3.12 с использованием Flask. Точка входа приложения создаётся фабрикой, что позволяет поднимать несколько независимых экземпляров в тестах.

3.2. Сервис предоставляет маршрут приёма запроса, стартовую страницу с описанием и интерактивную документацию.

3.3. Маршрут приёма запроса принимает тело в формате JSON и возвращает рекомендованную температуру вместе с сезоном, по которому выполнен расчёт.

3.4. Входные и выходные данные описываются схемами: схема запроса проверяет обязательность полей и допустимые значения, схема ответа задаёт состав полей результата, схема ошибки задаёт единый вид сообщения об отказе.

3.5. Схемы дополнительно описывают вход и выход типизированными словарями, чтобы назначение полей читалось в коде без обращения к документации.

3.6. Валидация выполняется до обращения к расчёту: при недопустимых данных расчёт не запускается.

3.7. Тело запроса, не являющееся объектом JSON, отклоняется с кодом 400. Это относится к пустому телу, массиву, строке и числу.

## 4. Требования к расчёту температуры

4.1. Расчёт строится на абстрактном классе TemperatureAdvisor, который объявляет метод расчёта, обязательный к реализации наследниками.

4.2. Абстрактный класс имеет трёх наследников: OfficeTemperature, HomeTemperature и WarehouseTemperature. Каждый наследник отвечает за свою норму температуры.

4.3. Выбор наследника выполняется по типу помещения через карту стратегий. Добавление нового типа помещения сводится к одному классу и одной строке в карте.

4.4. Значения норм хранятся отдельной таблицей, а не в коде методов расчёта: таблица связывает тип помещения и сезон с целым числом градусов.

4.5. Если для типа помещения нет наследника, служба расчёта возбуждает собственное исключение с текстом, перечисляющим допустимые типы.

4.6. Собственная иерархия исключений содержит базовое исключение сервиса и наследника для ошибок расчёта температуры. Исключение хранит текст и необязательные подробности.

## 5. Требования к структуре данных

5.1. Тип помещения и сезон описываются перечислениями со строковыми значениями. Перечисления используются и в схемах, и в таблице норм, поэтому список допустимых значений задаётся в одном месте.

5.2. Допустимые типы помещений: office, home, warehouse. Допустимые сезоны: winter, spring, summer, autumn.

5.3. Входной словарь содержит тип помещения и сезон, выходной словарь содержит рекомендованную температуру и сезон.

5.4. Рекомендованная температура передаётся целым числом, тип помещения и сезон строками.

## 6. Требования к интерфейсу

6.1. Стартовая страница сервиса содержит форму расчёта: список типов помещений, список сезонов и кнопку расчёта. Значения списков подписаны на русском языке, у каждого поля есть подпись.

6.2. Отправка формы выполняется без перезагрузки страницы: запрос уходит на маршрут расчёта, полученный ответ выводится на той же странице.

6.3. Результат расчёта выводится крупным числом с единицей измерения и пояснением, для какого помещения и сезона он получен.

6.4. Отказ сервиса выводится отдельным блоком с текстом причины, полученным от сервиса. Для недопустимого значения перечисляются допустимые.

6.5. На время запроса кнопка расчёта блокируется и меняет подпись, после ответа возвращается в исходное состояние.

6.6. Форма и результат отображаются на настольном и узком экране: при ширине до 620 пикселей поля выстраиваются в столбик, кнопка занимает всю ширину.

6.7. Интерактивная документация Swagger доступна по адресу /apidocs/ и содержит описание эндпоинта: назначение, поля тела запроса с примером, ответы с кодами и примеры значений. Документация позволяет отправить запрос из браузера.

6.8. Название и версия сервиса в документации совпадают с названием проекта.

## 7. Требования к обработке ошибок

7.1. Код 400 возвращается при теле, не являющемся объектом JSON, при пропущенном обязательном поле, при недопустимом значении поля и при лишнем поле, которого нет в схеме.

7.2. Тексты сообщений об ошибках валидации выводятся на русском языке, как и остальные ответы сервиса.

7.3. Код 404 возвращается для несуществующего маршрута, код 405 для неподдерживаемого метода. Оба ответа отдаются в формате JSON той же схемой ошибки, что и остальные отказы, а не страницей HTML.

7.4. Код 500 возвращается при ошибке расчёта, возбуждённой собственным исключением сервиса, и при непредвиденной ошибке. Текст непредвиденной ошибки наружу не выдаётся: клиент получает общее сообщение, подробности попадают в журнал приложения.

7.5. Форма ответа об ошибке одинакова для всех кодов: имя ошибки и подробности.

## 8. Требования к документированию

8.1. В состав поставки входит README с описанием назначения, таблицей норм, стеком, порядком установки и запуска, контрактом API с кодами ошибок, составом проверок и ограничениями.

8.2. В состав поставки входит настоящее техническое задание.

8.3. Проект распространяется по лицензии MIT.

## 9. Порядок контроля и приёмки

9.1. Проверки запускаются командой `pipenv run pytest` из каталога src, отдельный скрипт scripts/test делает то же самое.

9.2. Проверками подтверждается расчёт для всех двенадцати сочетаний типа помещения и сезона, выбор класса расчёта по карте стратегий, возбуждение собственного исключения для неизвестного типа помещения, соответствие таблицы норм заданным значениям, разбор схемы запроса, состав полей ответа, коды 400 для пустого тела, не-объекта JSON, пропущенного и недопустимого поля, лишнего поля, коды 404 и 405 в формате JSON, код 500 при ошибке расчёта.

9.3. Работоспособность подтверждается запуском сервиса и обращением к маршруту для всех двенадцати сочетаний, а также открытием страницы описания и документации Swagger.

9.4. Форма проверяется в браузере на ширине 1280 и 390 пикселей: расчёт через форму для трёх сценариев, вывод отказа при недопустимом значении, возврат кнопки в исходное состояние, отсутствие горизонтальной прокрутки, выстраивание полей в столбик на узком экране.

## 10. Требования к развёртыванию

10.1. Требуется Python версии 3.12 или новее: используются строковые перечисления.

10.2. Каталог src должен попадать в путь импорта, для этого задаётся переменная PYTHONPATH. Это же требование учитывают запуск под gunicorn и сборка контейнера.

10.3. Зависимости объявляются в Pipfile и закрепляются файлом блокировки.

10.4. Промышленный запуск выполняется под gunicorn; число рабочих процессов задаётся переменной окружения, по умолчанию один.

10.5. Предусмотрен запуск в контейнере: образ собирается из каталога src, исходники монтируются только для чтения, порт 9030 публикуется наружу. Скрипты запуска, остановки и удаления контейнера лежат в каталоге scripts.

11.4. Учёт температуры на улице и влажности как дополнительных условий расчёта.

11.5. Ограничение частоты запросов и ключи доступа для внешних клиентов.
